# Asset Compass リリース手順

この文書は、Asset Compassの変更を実装からリリースまで進めるためのチェックリストです。レビューは実装コミットを基準点とし、最終リリースコミットの前に必要な修正・文書・バージョン履歴を揃えます。

## 基本フロー

```text
実装
↓
動作確認・微調整・テスト
↓
実装コミット
↓
差分コードレビュー
↓
レビュー指摘の修正
↓
必要に応じて再レビュー
↓
再テスト（全テスト成功を確認）
↓
関連する設計書・仕様書とロードマップの更新
↓
コミットメッセージ決定
↓
バージョン履歴作成
↓
assets/version-history.json 更新
↓
PC / スマートフォンで履歴表示確認
↓
最終確認
↓
リリースコミット
↓
必要に応じてプッシュ
```

## 1. 実装

- [ ] 対象バージョンで実施する機能・修正の範囲を確認する。
- [ ] 合意した仕様に沿って実装する。
- [ ] PCとスマートフォンの表示・操作を考慮する。
- [ ] データ構造、保存方式、API連携、広範囲に影響する設計判断は人間が確認する。

## 2. 動作確認・微調整・テスト

- [ ] PC表示と主要な操作を確認する。
- [ ] スマートフォン表示と主要な操作を確認する。
- [ ] 必要な微調整を行う。
- [ ] 変更に関連するテストを実行する。
- [ ] 原則として、リリース前に全テストが成功していることを確認する。
- [ ] テストの期待値が現在の仕様に合っていることを確認する。古い仕様を守るだけのテストは、現在の仕様に合わせて更新する。

## 3. 実装コミット

- [ ] 動作確認と関連テストが済んだ実装を一度コミットする。
- [ ] このコミットをコードレビューの基準点にする。
- [ ] コミット後の作業ツリーに、レビュー対象外の変更が混ざっていないことを確認する。

レビュー対象の差分は、原則として直前コミットと実装コミットの比較にします。

```sh
git diff HEAD~1 HEAD
```

## 4. Codexによるコードレビュー

- [ ] 直前コミットとの差分を確認し、今回変更された箇所を中心にレビューする。
- [ ] バグの可能性を確認する。
- [ ] 保守性と重複コードを確認する。
- [ ] 非同期処理とエラー時の挙動を確認する。
- [ ] LocalStorageやその他の保存データへの影響を確認する。
- [ ] Yahoo Finance APIなど外部API連携への影響を確認する。
- [ ] PC / スマートフォンの表示差分を確認する。
- [ ] セキュリティ上の懸念を確認する。
- [ ] テスト不足や、既存テストと現行仕様の不整合を確認する。
- [ ] 指摘には重要度（高・中・低）、対象ファイル、理由を付ける。

## 5. レビュー指摘の修正

- [ ] 必要な指摘だけを修正する。
- [ ] 修正によって仕様やテスト期待値に変更が必要になった場合は、現行仕様に合わせて更新する。
- [ ] 仕様変更時は、既存テストが古い仕様を期待していないか確認し、現行仕様に合う期待値へ更新する。テストを通すためだけに実装を旧仕様へ戻さない。
- [ ] 修正後にPC / スマートフォンの動作を再確認する。
- [ ] 指摘修正で追加差分が生じた場合は、必要に応じて再レビューする。
- [ ] 再レビューを含む修正確認の後、関連テストと全テストを実行し、全テスト成功を確認する。

## 6. 設計書・仕様書・ロードマップの更新

- [ ] レビュー後の最終実装を基準に、今回の変更に関係するMarkdownだけを更新する。
- [ ] 影響のない文書を機械的に更新しない。
- [ ] 必要に応じて `architecture.md`、`data-design.md`、`feature-spec.md`、`screen-design.md` などを更新する。
- [ ] ロードマップ上の項目に影響する場合は `roadmap.md` を更新する。
- [ ] リリース手順自体に変更がある場合は、この `release-flow.md` を更新する。
- [ ] 実装コミットとの差分を参照し、ドキュメント更新漏れがないか確認する。

## 7. コミットメッセージ決定

- [ ] 対象バージョンの変更内容を表す最終コミットメッセージを決める。
- [ ] 英語で簡潔に記述する。

例：

```text
Add asset goal simulation details and yearly returns
```

## 8. バージョン履歴作成

- [ ] バージョン番号、リリース日、コミットメッセージ、主な変更点をまとめる。
- [ ] まずChatGPT内の「Asset Compassバージョン履歴」用メモを作成する。
- [ ] 変更点は利用者に伝わる粒度に整理する。

## 9. `assets/version-history.json` 更新

- [ ] バージョン履歴メモと同じ内容をJSON形式にする。
- [ ] `assets/version-history.json` の既存データ構造に合わせて追加する。
- [ ] 最新バージョンが先頭にあることを確認する。
- [ ] JSONとして読み込み可能であること、日付・バージョン・変更内容に誤りがないことを確認する。
- [ ] PC / スマートフォンの入口に表示する現在バージョンが、履歴の最新バージョンと一致することを確認する。

## 10. バージョン履歴の表示確認

- [ ] PC版のバージョン履歴モーダルを確認する。
- [ ] スマートフォン版のバージョン履歴画面を確認する。
- [ ] バージョン番号、日付、コミットメッセージ、変更内容がJSONと一致することを確認する。
- [ ] JSON読み込みエラーがないことを確認する。
- [ ] 履歴表示にレイアウト崩れがないことを確認する。

## 11. 最終確認

- [ ] `git status` で変更ファイルを確認する。
- [ ] 不要な変更ファイルやローカルデータが含まれていないことを確認する。
- [ ] テスト結果と必要な構文・差分チェックを確認する。
- [ ] 関連する設計書・仕様書・ロードマップに更新漏れがないことを確認する。
- [ ] `assets/version-history.json` と履歴メモの内容が一致することを確認する。
- [ ] PC / スマートフォンで対象機能と履歴表示に問題がないことを確認する。

## 12. リリースコミットとプッシュ

- [ ] レビュー修正、関連ドキュメント、バージョン履歴を含めて最終確認する。
- [ ] 対象バージョンのリリースコミットを作成する。
- [ ] 必要に応じてGitHubなどのリモートへプッシュする。

## 運用ルール

- レビューは原則として、実装コミットとその直前コミットとの差分を中心に行う。
- 重要な設計判断はAI任せにせず、人間が確認する。特にデータ構造、保存方式、API連携、広範囲に影響する設計変更は慎重に扱う。
- テストコードも仕様変更に合わせて更新する。古い仕様を期待するテストが残っていないか確認する。
- 全テスト成功をリリース前の基本条件とする。
- 設計書・仕様書はレビュー後の最終実装を正として更新する。
- バージョン履歴メモと `assets/version-history.json` の内容を一致させる。
- 仕様書・設計書は今回の変更に関係するファイルだけを更新する。
- 原則として `v0.X.9` はリファクタリング、レイアウト調整、技術的負債の整理、小さな不具合修正に使う。
- 新機能追加と整備回を分け、各機能ブロックを安定させながら `v1.0.0` を目指す。
